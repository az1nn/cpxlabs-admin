# ADR-0014 — Observability, Correlation and Durable Audit Boundary

**Status:** Accepted  
**Date:** 2026-09-09

## Context

The enterprise starter now has authenticated, server-authoritative mutations. Operational logs alone are not sufficient evidence for business mutations: logs can be sampled, rotated or unavailable, while audit records must remain durable and queryable after a subject is deleted.

## Decision

1. Every API request receives an application request id generated by the server and returned as `x-request-id`.
2. Error envelopes and structured security events use that same request id.
3. Durable domain audit is stored in PostgreSQL as append-only `AuditEvent` rows. The application exposes append/read operations only; no audit update/delete API exists.
4. Customer create/update/delete and their audit append execute inside the same PostgreSQL transaction in the Prisma reference adapter. A failure to persist the audit record rolls the customer mutation back.
5. Audit snapshots are explicit domain allowlists. Raw HTTP request bodies, headers, cookies, provider sessions, tokens and secrets are never persisted as audit metadata.
6. Audit records snapshot actor id/email/name and subject id rather than relying on foreign keys to mutable/deletable identity/domain rows.
7. Operational logs/security events, telemetry and durable audit remain separate concerns. OpenTelemetry does not replace the application request id or durable audit evidence.
8. `audit.read` is a project-owned capability granted to Admin only in the reference policy.

## Consequences

- The reference API gains a small application mutation service because repository-only CRUD cannot guarantee mutation+audit atomicity across two writes.
- Prisma transaction details remain inside `apps/api`; frontend/shared contracts remain ORM-independent.
- In-memory adapters remain useful for lightweight tests/demo execution, but PostgreSQL is the authority for the atomicity guarantee.
- Audit storage grows monotonically and requires operational retention/archival policy in a future production-specific deployment decision; deletion is intentionally not part of the application API.
